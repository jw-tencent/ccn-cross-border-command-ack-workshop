First understand the route; then measure it

What CCN is in this demo

CCN is the private connectivity layer between your Guangzhou and US cloud networks. It carries the middle segment after traffic has entered your Guangzhou cloud ingress.

What CCN is not

It is not a browser plug-in, a DNS switch, or a number that turns a browser ACK sample into a network-latency or SLA claim.

When this demo fits

Use it to learn a controlled private segment—not to make a generic speed claim.

Good fit: China Mainland users entering a US-hosted application through a Guangzhou front door; multi-region VPC private connectivity; a customer walkthrough that keeps the same application origin for Direct and routed testing.

Not a fit by itself: a one-server static website, generic CDN caching, an overseas-user-to-China-site pattern, or a browser-latency benchmark without comparable China Mainland client conditions.

The four things to build

Think of it as four jobs, not one giant network project.

01

US origin

Your static page, Nginx, and Node ACK service. Build this first.

02

Direct control

Public browser → US ACK service. Prove this works before CCN exists.

03

Guangzhou door

An EIP + CVM that accepts routed WSS and proxies only to the US private origin.

04

CCN middle

Approved VPC association, routes, and cross-border bandwidth between the two VPCs.

Build in this order

Eight steps from empty account to customer walkthrough.

Choose the lab design

Confirm non-overlapping VPC ranges, two hostnames, budget ownership, and a cleanup owner before you create cloud resources.

Optional local check

Technical owners can run the sample locally to confirm a Direct ACK before cloud resources are created.

npm run smoke

Prove Direct

Set directWs to the US WSS hostname. Run ten sequential commands and preserve both success and failure counts.

Build Guangzhou ingress

Create a non-overlapping Guangzhou VPC, CVM, EIP, separate DNS name, and TLS certificate. This host is a WSS door, not a second website.

Configure CCN

Create CCN, associate both VPCs, check routes, then complete the applicable compliance and bandwidth steps before enabling cross-border use.

Prove private path

From Guangzhou, check the US private origin with the expected TLS hostname/SNI. Fix CCN routes, security groups, or TLS before public browser testing.

Enable routed WSS

Configure Guangzhou Nginx to proxy /ws to the US private origin. Then set ccnPathWs in a deployment-only config file.

Test fairly

Use the same China Mainland client, browser, payload, US origin, and time window for Direct and routed tests.

Ready to enable ccnPathWs?

  • US Direct endpoint is healthy
  • Guangzhou VPC and US VPC CIDRs do not overlap
  • CCN association, routes, approval, and bandwidth are in place
  • Guangzhou can reach the US private origin
  • Both public hostnames have valid TLS/WSS
  • Guangzhou Nginx exposes only /healthz and /ws

Say this to customers

“This shows a real Command-to-ACK application exchange through the configured endpoint. It proves application continuity for this test condition.”

Do not say: “This number is CCN latency,” “this proves one-way delay,” or “this is an SLA guarantee.”

60-second customer talk track

1. The challenge: A China Mainland browser normally reaches a US service through a public path.

2. The design: Our routed path enters through Guangzhou, crosses the private CCN-connected segment, and reaches the same US origin.

3. The control: The Direct path reaches the same ACK service without that configured ingress and CCN segment.

4. The evidence: A result appears only after the matching ACK comes back to the browser.

5. The boundary: This is application-level test evidence, not standalone network-performance proof.
